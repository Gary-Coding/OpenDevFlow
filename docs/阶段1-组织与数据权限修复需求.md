# OpenDevFlow 阶段 1 修复需求：组织与数据权限闭环

## 1. 修复目标

当前阶段 1 已经实现了部分组织、数据权限、需求和工作流代码，但还没有形成可运行、可验收的“组织与数据权限闭环”。

本修复需求只针对阶段 1 不完善内容，不扩展后续 MVP 功能。

修复完成后，应满足：

- 干净数据库启动后，组织、部门、角色数据范围、用户归属和权限初始化完整可用。
- 后端可以正确获取 ORM `User`，并基于其角色、公司、部门计算数据范围。
- 管理员可以维护部门。
- 管理员可以在用户管理中设置用户所属部门。
- 管理员可以在角色管理中设置数据范围和自定义部门。
- 需求列表、详情、工作流相关接口的数据权限可运行。
- 第一阶段相关操作有审计记录。

## 3. 当前已发现的问题

### 3.1 SQL 初始化没有执行新增脚本

当前 `docker-compose.yml` 只挂载：

```text
backend/sql/init.sql
```

但新增脚本：

```text
backend/sql/001_add_organization.sql
backend/sql/002_add_repositories.sql
backend/sql/003_add_demands_workflows.sql
backend/sql/004_add_artifacts_runs_reviews.sql
backend/sql/005_init_data.sql
```

不会在干净数据库中自动执行。

修复要求：

- 方案一：把新增 SQL 合并进 `backend/sql/init.sql`。
- 或方案二：修改 `docker-compose.yml`，挂载整个 `backend/sql` 目录到 `/docker-entrypoint-initdb.d`，并保证脚本按顺序执行。

建议使用方案二。

验收：

- 删除旧数据库 volume 后重新 `docker compose up -d postgres`。
- 数据库中存在 `companies`、`departments`、`role_departments`、`demands`、`workflows` 等表。
- 默认公司、默认部门存在。
- admin/user 角色存在且 `data_scope` 正确。
- admin/user 用户绑定默认公司和默认部门。

## 4. 当前用户加载修复

### 4.1 问题

当前 `get_current_user()` 返回的是 JWT 中解析出的 `CurrentUser` dataclass：

```text
id
roles
menus.permission
username
display_name
```

它不是 ORM `User`，没有：

```text
company_id
department_id
roles[].data_scope
roles[].custom_departments
```

但 `demands/router.py` 和 `data_scope.py` 把它当成 ORM `User` 使用，运行时会出错。

### 4.2 修复要求

保留现有 `CurrentUser` 用于轻量认证和 RBAC。

新增一个依赖函数，例如：

```text
get_current_orm_user()
```

职责：

- 从 token 中解析用户 id。
- 从数据库加载 ORM `User`。
- 预加载 roles、menus、company、department、roles.custom_departments。
- 用户不存在或停用时返回 401。

建议放在：

```text
backend/app/modules/auth/dependencies.py
```

或：

```text
backend/app/core/current_user.py
```

业务接口需要数据权限时必须使用 ORM 用户：

```text
current_user: User = Depends(get_current_orm_user)
```

RBAC 权限校验仍可继续使用 `require_permissions()`。

验收：

- 创建需求接口可以读取 `current_user.company_id` 和 `current_user.department_id`。
- `apply_demand_data_scope()` 能读取 `current_user.roles[*].data_scope`。
- `check_demand_data_permission()` 能正常运行。

## 5. 组织与部门 API

### 5.1 新增部门 API

新增模块：

```text
backend/app/modules/departments/router.py
```

并在：

```text
backend/app/api/v1/router.py
```

挂载：

```text
/departments
```

API：

- `GET /departments`
- `POST /departments`
- `PATCH /departments/{id}`
- `DELETE /departments/{id}`

### 5.2 字段

创建/编辑字段：

- `parent_id`
- `name`
- `order_num`
- `status`

不允许前端传 `company_id`。

创建时：

- `company_id` 使用当前管理员的 `company_id`。
- `ancestors` 根据父部门自动计算。

如果无父部门：

```text
ancestors = ''
```

如果有父部门：

```text
ancestors = parent.ancestors + ',' + parent.id
```

注意避免前导多余逗号。

### 5.3 删除限制

删除部门时：

- 如果存在子部门，不允许删除。
- 如果存在用户绑定该部门，不允许删除。

### 5.4 权限

- `GET /departments`: `system:department:list`
- `POST /departments`: `system:department:create`
- `PATCH /departments/{id}`: `system:department:update`
- `DELETE /departments/{id}`: `system:department:delete`

### 5.5 审计

写入：

- `system.department.create`
- `system.department.update`
- `system.department.delete`

## 8. 数据权限 helper 修复

### 8.1 当前问题

`get_department_and_children_ids()` 使用：

```text
Department.ancestors.contains(str(department_id))
```

如果 ancestors 是简单字符串，可能出现误匹配风险。

### 8.2 修复要求

MVP 可以保留字符串 ancestors，但要统一格式，推荐：

```text
ancestors = 'root_id,parent_id'
```

查询子部门时建议使用：

```text
ancestors == str(department_id)
or ancestors like f'{department_id},%'
or ancestors like f'%,{department_id},%'
or ancestors like f'%,{department_id}'
```

或者在 PostgreSQL 中将 ancestors 保存为逗号分隔后用更明确的匹配条件。

### 8.3 公司边界

所有数据范围过滤都必须限定当前公司：

- `all`: 当前公司全部需求。
- `dept`: 当前公司 + 当前部门。
- `dept_and_child`: 当前公司 + 当前部门及下级部门。
- `custom_dept`: 当前公司 + 自定义部门。
- `self`: 当前公司 + 当前用户创建。

## 9. 需求与工作流接口权限修复

当前需求和工作流接口只依赖登录，没有功能权限校验。

修复要求：

需求接口增加：

- `GET /demands`: `demand:list`
- `POST /demands`: `demand:create`
- `GET /demands/{id}`: `demand:list`
- `PATCH /demands/{id}`: `demand:update`
- `DELETE /demands/{id}`: `demand:delete`
- `POST /demands/{id}/archive`: `demand:archive`

工作流接口增加：

- `GET /demands/{id}/workflow`: `workflow:view`
- `POST /demands/{workflow_id}/advance`: `workflow:advance`
- `POST /demands/{workflow_id}/block`: `workflow:block`

注意：

- 功能权限通过 `require_permissions()` 校验。
- 数据权限通过 `check_demand_data_permission()` 校验。
- 两者都必须满足。

## 10. 工作流阶段规则修复

当前 `advance_workflow()` 没有完整处理 delivered/archived 状态。

修复要求：

- 当前阶段推进到 `final_review` 时，不自动设置 delivered。
- 当前阶段从 `final_review` 推进到 `archived` 前，应优先通过归档接口处理。
- 归档接口执行时：
  - `demand.status = archived`
  - `workflow.status = archived`
  - 当前阶段如果不是 `archived`，应把当前阶段置为 `passed`
  - `archived` 阶段置为 `passed`
  - `workflow.current_stage = archived`

如果保留从 `final_review` 手动推进到 `archived`，则必须同步：

- `demand.status = delivered` 或 `archived`
- `workflow.status = done` 或 `archived`

建议 MVP 简化：

- 普通推进不能进入 `archived`。
- 归档只能通过 `POST /demands/{id}/archive`。

## 14. 验收用例

### 14.1 干净数据库初始化

步骤：

1. 删除 PostgreSQL volume。
2. 执行 `docker compose up -d postgres`。
3. 连接数据库检查表和初始化数据。

期望：

- `companies` 有默认公司。
- `departments` 有默认部门。
- `roles.data_scope` 存在。
- `admin` 角色为 `all`。
- `user` 角色为 `self`。
- admin 用户绑定默认公司和默认部门。

### 14.2 用户部门绑定

步骤：

1. 管理员登录。
2. 创建一个新部门。
3. 创建一个普通用户并选择该部门。
4. 查看用户列表。

期望：

- 用户列表显示所属部门。
- 数据库中用户 `department_id` 正确。
- 审计日志记录用户创建。

### 14.3 角色数据范围

步骤：

1. 管理员编辑普通用户角色。
2. 设置数据范围为 `dept_and_child`。
3. 保存。
4. 再次打开角色编辑弹窗。

期望：

- 数据范围保存成功。
- 再次打开能正确回显。
- 审计日志记录角色更新。

### 14.4 自定义部门数据范围

步骤：

1. 创建两个部门 A 和 B。
2. 编辑某角色，设置数据范围为 `custom_dept`。
3. 选择部门 A。
4. 保存后重新打开。

期望：

- 只回显部门 A。
- `role_departments` 中只保存该角色和部门 A 的关系。

### 14.5 需求数据权限

步骤：

1. admin 创建两个普通用户，分别属于部门 A 和部门 B。
2. 用户 A 创建需求 A。
3. 用户 B 创建需求 B。
4. 用户 A 使用默认 `self` 数据范围查询需求列表。
5. 将用户 A 的角色数据范围改为 `dept`。
6. 再次查询需求列表。

期望：

- `self` 时只能看到自己创建的需求。
- `dept` 时只能看到本部门需求。
- 不能看到其他部门需求。

### 14.6 工作流权限

步骤：

1. 使用没有 `workflow:advance` 权限的用户请求推进工作流。
2. 使用有 `workflow:advance` 权限但无数据可见性的用户请求推进别人的需求工作流。

期望：

- 缺功能权限返回 403。
- 缺数据权限返回 403。

### 14.7 前端基础检查

步骤：

1. 登录管理员。
2. 打开组织管理。
3. 打开用户管理。
4. 打开角色管理。

期望：

- 可以维护部门。
- 用户表单可以选择部门。
- 角色表单可以选择数据范围。
- `custom_dept` 时显示部门多选。
